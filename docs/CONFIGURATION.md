# Configuration reference

This is the reference for every setting that means something on the
handheld: the settings in `halo/config.toml`, each with its type, default,
environment variable and effect, and the `HALO_*` environment variables that
the host and the renderer read directly. It is generated by hand from the
settings table in `port/linux/src/port_config.c` (`config_settings`), from
`port/knulli/host/*.c` and from the launcher, `port/knulli/Halo.sh`. Players
mostly need `display.render_scale`; the `debug.*` switches and the
variables at the end are for measuring and developing the port
([Profiling](PROFILING.md)).

## How the settings work

**The file.** The settings are in `config.toml` in the data folder,
`/userdata/roms/ports/halo/`. At the first launch, `Halo.sh` writes seven
values for the handheld if the file is missing:

```toml
[display]
screen_width = 0
render_scale = 0.75
interpolation = true
fast_shaders = true
fast_textures = true

[update]
auto = false

[network]
online = false
```

When the game starts, it reads the file once (`config_load`). Every
setting of this build that the file lacks is added in its section at its
default, with its comment, and the log says so:

```
settings: added display.model_detail (new in this version) at its default
```

Apart from that, the game never rewrites the file, so your edits and
comments stay. Change settings while the game is not running.

**Types.** A boolean is `true` or `false`. An integer is a whole number
without a decimal point. A real accepts `0.75` or `1`. A string is quoted.
A value of the wrong type is reported in the log with its line number and
the default is used instead, for example:

```
W halo: halo-linux: config.toml line 131: debug.draw_callers should be a whole number; using 0
```

Keys that are no setting are reported as `unknown setting`. If the file is
not valid TOML at all, the log says so and every setting takes its default.

**Environment variables.** Each setting has a `HALO_*` environment variable
that overrides the file for one run. The host passes every `HALO_*`
variable of its environment to the game (up to 64 variables in all). There
are three styles:

| Style | Meaning |
| --- | --- |
| value | The variable's text is the value. For a boolean, `0`, `false`, `no` and `off` (in any case) are false and anything else is true. |
| set is true | The variable being set at all, to anything, makes the boolean true. `HALO_DEBUG_TINY_SCISSOR=0` still turns it on. |
| set is false | The variable being set at all makes the boolean false (`HALO_NO_VSYNC`, `HALO_NO_AUDIO`). |

On the handheld, the game is started by `Halo.sh`, so to set a variable for
normal play, add `export HALO_NAME=value` to `Halo.sh` before the line
`./halo`. For measurements, `tools/bench.sh` passes `HALO_NAME=value`
arguments to the game ([Profiling](PROFILING.md)).

**Defaults.** "Default" below is the value in the settings table, which is
what the game uses when neither the file nor a variable sets it. Where the
launcher writes another value, the table says so.

## Display

### `display.render_scale`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| real | `1.0` | `0.75` | `HALO_RENDER_SCALE` |

The 3D picture's resolution as a fraction of the screen's, from 0.5 to 1.0.
Render targets the size of the screen get this fraction of the pixels in
each direction, and Present scales the picture up to the display with linear
filtering (`screen_mode_choose` in `d3d8_gl.c`). At 0.75 on a 640x480
screen the game draws 480x360, and the log says
`screen: 640x480 drawn at 480x360`. The whole picture is drawn at this
scale, the HUD and menus included. Values below 0.5 become 0.5, and values
above 1.0 become 1.0. It also scales `display.model_detail`.

**When to change it.** This is the main trade between sharpness and speed.
At 1.0 the GPU's pixel and vertex work limits the frame rate (about 24 to
40 fps in the campaign); at 0.75 the limits are the CPU-side
threads; see the [README's performance table](../README.md#performance).
Lower it for more headroom in heavy scenes or when the handheld is hot.
`display.dynamic_resolution` lowers it on its own where the GPU is the
limit.

### `display.dynamic_resolution` and `display.dynamic_resolution_min`

| Setting | Type | Default | Variable |
| --- | --- | --- | --- |
| `display.dynamic_resolution` | boolean | `true` | `HALO_DYNAMIC_RESOLUTION` |
| `display.dynamic_resolution_min` | real | `0.5` | `HALO_DYNAMIC_RESOLUTION_MIN` |

While the GPU falls behind, the picture is drawn below
`display.render_scale`, a step of 1/16 at a time, down to
`dynamic_resolution_min`; once the GPU keeps up again, the steps come back
one at a time ([Architecture](ARCHITECTURE.md#render-targets-and-the-render-scale)).
Each change shows in the log as a `screen: ... drawn at` line. It needs
the Knulli host's GL thread, and it never raises the picture above
`render_scale`.

The GPU limits only some scenes. In the c10 opening at render scale 0.75 it
did, at 30 to 42 fps; at 0.625 the same scene ran at about 56 fps, and at
0.5 at a steady 60. In the a30 opening the GPU falls behind in the first
seconds, and the scale is back at `render_scale` about 20 seconds in. In
the b30 battle the CPU-side threads are the limit, and the scale steps down
only briefly. At `render_scale = 1.0` it holds the b30 battle at 480x360 to
520x390 for much of the fight, but it does not help the a30 opening after
its intro: the GPU limits it there, but the GL thread waits for it where
dynamic resolution does not see it
([Roadmap](ROADMAP.md#3-the-gpu-and-the-picture)).

**When to change it.** Raise `dynamic_resolution_min` (up to
`render_scale`) for a sharper picture in heavy scenes at a lower frame rate,
or turn it off to keep the picture at `render_scale` at all times. Values
below 0.5 become 0.5.

### `display.model_detail`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| real | `0.5` | (not written; the default applies) | `HALO_MODEL_DETAIL` |

How early objects switch to their simpler models, as a fraction of the size
at which the game itself switches (1.0), multiplied by
`display.render_scale`. The game picks a model's detail level by comparing
the object's size on screen with the model's cutoffs; the port multiplies
the size by this product first (`xgpu_model_detail_scale`,
`source/models/models.c`), so objects look as detailed as the pixels that
are actually drawn allow. The value is clamped to 0.1 to 1.0.

**When to change it.** Models are most of the GPU's vertex work. In the a30
opening, on an earlier build at render scale 0.75, the frame rate was 24.0
at 1.0, 25.3 at 0.5 and 26.4 at 0.3. Lower it for large scenes; raise it
to 1.0, with `render_scale = 1.0`, for the game's own switch points.

### `display.fast_shaders`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `true` | `true` | `HALO_FAST_SHADERS` |

Computes colours in half precision, which Mali GPUs do at twice the rate.
The pixel shaders' default precision becomes `mediump`: colours, texels and
the combiners' arithmetic, all within [-1, 1]. Texture coordinates, fog and
the uniforms that feed coordinates stay single precision. The vertex
shaders' colour outputs are `mediump` too. `false` keeps single precision
everywhere. Read once at start-up.

**When to change it.** Half and single precision gave the same GPU time
within the noise in the measurements (about 12.6 and 13 fps in GPU-timed
b30 runs), so it stays on because it costs nothing. Turn it off to rule it
out when you investigate a colour fault.

### `display.fast_textures`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `true` | `true` | `HALO_FAST_TEXTURES` |

Gives the GPU DXT1 and 16-bit Xbox textures as 16-bit texels, the colours
they hold, rather than 32-bit ones (`texels_pack` in `xbox_textures.c`):
DXT1 as RGB565, or RGB5A1 when it has transparent texels; the 16-bit formats
as RGB565, RGB5A1 or RGBA4 by their layout. The picture is the same; the
texture memory and the bandwidth of each lookup are halved. Takes effect
for textures decoded after start-up, so change it between runs.

**When to change it.** Texture bandwidth was not what limited the GPU in the
measurements ([Performance](PERFORMANCE.md)), but the setting halves the
texture memory on a 1 GB device. Keep it on.

### `display.screen_width`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| integer | `0` | `0` | `HALO_SCREEN_WIDTH` |

The number of columns of the 480-line picture: 640 for the Xbox's 4:3, or
0 for the display's shape. For 0, the host computes the width from the
framebuffer's first mode (`/sys/class/graphics/fb0/modes`) as 480 times the
longer side over the shorter one, and passes it as `HALO_DISPLAY_WIDTH`; on
a 640x480 screen that is 640. With a wider picture the 3D view widens (the
camera keeps its vertical field of view), and the menus stay 640 columns
wide in the centre. The picture is centred on the screen.

**When to change it.** The launcher writes 0, which fills any screen: 640
columns on the 4:3 handhelds, 720 on the RG34XX models' 720x480 (reported
on the RG34XX SP, [issue #1](https://github.com/kirklandsig/halo-ce-anbernic-rg35xx/issues/1)). Set 640 for the
Xbox's 4:3 picture on a wider screen. Installs from before 2026-10-02 have
640 written; change it to 0 on a 3:2 handheld.

### `display.vsync`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `true` | (not written; the default applies) | `HALO_NO_VSYNC` (set is false) |

Waits for the display between frames (a swap interval of 1); `false` draws
as fast as possible. The host's `HALO_SWAP_INTERVAL` overrides the swap
interval the game asks for. Frames are paced to the display only with vsync
([`display.frame_pacing`](#displayframe_pacing)).

**When to change it.** For measurements only. When a thread or the GPU is
the limit, turning it off changes little: in the a30 opening on an earlier
build, every frame took 22 to 28 ms with and without vsync.

### `display.interpolation`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `true` | `true` | `HALO_INTERPOLATION` |

Draws a frame for every display refresh, blending between the game's 30
ticks a second; `false` keeps the original 30 frames a second.

**When to change it.** `false` holds the game at 30 frames a second, one a
tick: every frame stays on screen for two refreshes, the most even motion
this display allows. `true` draws more frames (45 to 60 in most of the
campaign at render scale 0.75), but where the GPU or the game's thread falls
behind, a frame is shown a refresh later than it was drawn for, and the
motion steps (in the b30 battle about one frame in six; see
[Architecture](ARCHITECTURE.md#frame-pacing)). A matter of taste.

### `display.frame_pacing`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `true` | | `HALO_FRAME_PACING` |

Shows each frame at the display refresh it was drawn for: the game takes
the refresh a frame is due at as its clock for the frame, and the GL thread
holds a frame that is ready early until then
([Architecture](ARCHITECTURE.md#frame-pacing)). Most frames then show the
world as it is when they are seen: in the b30 battle the time between the
two stays the same from one frame to the next on 83% of frames, against 52%
unpaced, and a frame the GPU finishes too late (and the frames after it)
is shown a refresh late. It needs the Knulli host on an H700
handheld's own screen (it reads where the display is in its refresh from
the LCD timing controller) and vsync; elsewhere frames are not paced.

**When to change it.** `false` shows each frame as soon as it is drawn: the
same frame rate, with small timing errors on a third of the frames instead
of fewer, larger ones (in the b30 battle, whole-refresh steps on 11% of
frames against 17% paced). Try both.

### `display.high_res_hud`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `false` | `false` | `HALO_HIGH_RES_HUD` |

Upstream's high-resolution HUD: the meters, counters, motion sensor,
reticles, waypoints and scopes drawn from redrawn textures 8 times the size
of the maps' bitmaps (`hud_hires.c`). At the handheld's 640x480 it looks the
same, and in a30 it took 77 MB more memory and about 1 fps, so it is off
here by default (upstream's other builds have it on).

### `display.high_res_text`

| Type | Default | Launcher | Variable |
| --- | --- | --- | --- |
| boolean | `false` | `false` | `HALO_HIGH_RES_TEXT` |

Upstream's high-resolution text: the menus' and the HUD's text drawn with
TrueType fonts (Overpass, `port/assets/fonts`) rather than with the maps'
bitmap fonts, and the menus' titles from redrawn pictures
(`port/assets/titles`; `text_hires.c`, `hud_hires.c`). The glyphs are drawn
at the render targets' scale, which on the desktop is the display's and on
the handheld `display.render_scale`'s: at 0.75 the text is a different font,
not a sharper one. In a30 on the RG35XX
H it made no difference to the frame rate once the level ran, but the
level's first five seconds ran at 20 to 25 fps (against 60) while its
glyphs were drawn, and the game held about 100 MB more memory (435 to 452 MB
resident against 341). At the menus it costs more: launched from
EmulationStation, which stays in memory while a port runs, the game held
465 to 486 MB against 207 to 230, with about 250 MB of memory left against
560. With this on, the 1 GB ran out as a level started: the kernel killed
the game (exit status 137). So it is off here by default
(upstream's other builds have it on). v2026.10.02 added it to an existing
`config.toml` on: set it to `false` there if the game stops with exit
status 137.

### `display.player_names` and `display.player_name_scale`

| Setting | Type | Default | Variable |
| --- | --- | --- | --- |
| `display.player_names` | string | `"all"` | `HALO_PLAYER_NAMES` |
| `display.player_name_scale` | real | `1.0` | `HALO_PLAYER_NAME_SCALE` |

Upstream's names above the players' heads in multiplayer: `"all"`,
`"allies"`, `"enemies"` or `"none"` (an enemy's shows only while in sight
and not camouflaged), drawn at `display.player_name_scale` times the size
of the HUD's text (0.25 to 4). The campaign does not show them.

## Renderer switches

These `debug.*` settings were added for the Mali port (they are written only
in the Android and Knulli builds). The first five are optimisations, on by
default, that can be turned off to measure them or to rule them out when
something draws wrongly. The rest are instruments: they change the picture
on purpose to measure a cost. `gl_initialize` in `d3d8_gl.c` reads them
once, when the GL context is made.

### `debug.sort_models`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_SORT_MODELS` |

Draws the objects' models sorted by shader, rather than object by object
(`rasterizer_xbox_models.c`, [Architecture](ARCHITECTURE.md#models-sorted-by-shader)).
Objects that can be drawn in any order are kept between the model phase's
begin and end and their parts drawn sorted by shader, permutation and
geometry, which spares the GPU driver most of its changes of program. In
the a30 opening it cut the program switches from about 190 to 109 a frame
and the texture binds from 594 to 393.

### `debug.instance_models`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_INSTANCE_MODELS` |

Draws consecutive draws of the same skinned model part that differ only in
their constants (several marines' same part) as one instanced draw
(`d3d8_gl.c`, [Architecture](ARCHITECTURE.md#instanced-model-draws)). In
the a30 opening, 250 draws a frame become 57 instanced draws. `false` draws
each by itself.

### `debug.alpha_test_elision`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_ALPHA_TEST_ELISION` |

Draws without the alpha test when it cannot fail: the alpha tested is an
opaque texture's, read as it is, and the test passes for an alpha of 1
(`alpha_test_cannot_fail` in `d3d8_gl.c`). A shader that can discard loses
Mali's hidden surface removal. With it the a30 opening went from 36 to
40 fps on the build of the time; without it, it stayed at 36.

### `debug.batch_quads`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_BATCH_QUADS` |

Draws consecutive quad draws of the same state (decals) as one: their
vertices are copied together, and the constant attributes that differ
between them become per-vertex arrays (`batch_add`, `batch_flush`). In a
b30 battle, batches of about 500 quad draws became 21 to 65 draws. `false`
draws each quad draw by itself. Batching is also off for the frame that
`debug.gpu_trace_frame` traces.

### `debug.stable_streams`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_STABLE_STREAMS` |

Points indexed draws' attributes at their base vertex, so that draws from
one vertex buffer share them and the driver does not set them up again
(`setup_streams_rebased`). It applies only when every stream of the draw is
in the mirror and the context has base-vertex draws (OpenGL ES 3.2, which
the Mali-G31 driver has).

### `debug.no_program_cache`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `false` | `HALO_NO_PROGRAM_CACHE` |

Does not keep linked shader programs in `save/shaders/`; every start
compiles them again, about 220 to 250 ms of a core for each new
combination, on the program builder's thread: what they draw appears late
the first time. Use it only to test the compiler path; deleting
`save/shaders/` clears the cache without it.

### `debug.freeze`

| Type | Default | Variable |
| --- | --- | --- |
| string | `""` | `HALO_DEBUG_FREEZE` |

A comma-separated list of `textures`, `program` and `raster`. Once the
renderer has presented 600 frames, draws keep the textures and samplers,
the program, or the raster state (viewport, scissor, depth, stencil,
blending) they find, instead of setting their own (`debug_frozen`). The
picture is wrong, but every draw stays valid, so the frame rate shows what
setting that state costs the driver. The setting's comment says "after 20
seconds"; the code counts frames, so the delay is 20 seconds only at
30 fps.

In the a30 opening on the build that ran at 40 fps, `textures` alone left
40 fps, and `textures,program` gave 53 to 55 fps: program switches were the
driver's biggest cost per draw.

### `debug.tiny_scissor`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `false` | `HALO_DEBUG_TINY_SCISSOR` (set is true) |

Draws one pixel of each draw: every scissor rectangle becomes 1x1. The
vertices and the tiler still run, so the GPU's time without the pixels is
left. In the GPU-timed b30 run at 640x480, it took the frame rate from about
12.5 to about 22 fps. Because the variable's style is "set is true",
`HALO_DEBUG_TINY_SCISSOR=0` also turns it on; leave the variable unset
instead.

### `debug.lod_bias`

| Type | Default | Variable |
| --- | --- | --- |
| real | `0.0` | `HALO_DEBUG_LOD_BIAS` |

Added to every texture lookup's mip level, on top of the game's own bias:
4 samples levels 16 times smaller in each direction. It measures what
texture bandwidth costs:
in the GPU-timed b30 run, a bias of 4 changed about 12.5 to about 13 fps.

### `debug.draw_callers`

| Type | Default | Variable |
| --- | --- | --- |
| integer | `0` | `HALO_DEBUG_DRAW_CALLERS` |

Logs which code makes the draws, every 300 frames. The setting's comment
lists 1 and 2; the code also has 3 and 4:

| Value | Effect |
| --- | --- |
| `1` | Counts the draws and vertices of each caller of the draw functions, and logs the 24 busiest callers' draws per frame. |
| `2` | The same, one level up: the callers' callers. |
| `3` | As 2, and also logs how many indexed draws a frame repeat another draw of the frame (the same vertex shader, textures, vertex buffer, index data and count, primitive, blending, culling and pixel shader layout, with other constants), and every 600 model phases how the model sorting fares. |
| `4` | As 3, and repeated indexed draws are not drawn, to measure what drawing them as instances could gain (the picture misses them). |

The addresses are in the guest image; [Profiling](PROFILING.md#halo_debug_draw_callers)
shows how to read them. The value must be a whole number: `1.0` is
rejected with a message in the log.

### `debug.hitch_log`

| Type | Default | Variable |
| --- | --- | --- |
| real | `0.0` | `HALO_HITCH_LOG` |

Logs every frame longer than this many milliseconds, with what it did that
a smooth frame does not, and every 600 frames a summary; 0 never. The
renderer's line splits the frame into the game's work, the drawing and the
wait before it, and counts the programs, textures (with their bytes and
time), shaders and geometry made in it. The host reads the variable for its
two lines (the game's thread's waits, and the GL thread's slowest calls and
the draws it skipped), so set `HALO_HITCH_LOG` rather than the file's
setting to have all three. [Profiling](PROFILING.md#the-hitch-log) has
examples.

### `debug.async_textures`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_ASYNC_TEXTURES` |

Decodes textures and uploads them on a thread of their own, with a GL
context of its own, rather than on the game's thread with the uploads
queued to the GL thread. What a texture is drawn on appears once the
texture is in, a frame or a few after it is first needed. A texture the game
writes after it was uploaded, such as the glyph cache its text is drawn
from, is uploaded again on the game's thread, ahead of the draws that use
it. Uploaded again by the worker, the text drawn meanwhile used the glyphs
the texture held before, and came out garbled
([issue #1](https://github.com/kirklandsig/halo-ce-anbernic-rg35xx/issues/1)).
It needs the Knulli host's GL thread (with `HALO_GL_THREAD=0` textures are
uploaded as before).

### `debug.async_shaders`

| Type | Default | Variable |
| --- | --- | --- |
| boolean | `true` | `HALO_ASYNC_SHADERS` |

Translates shaders on a thread of their own, drawing what uses one only
once it is in, rather than on the game's thread when it is first drawn with
(about 0.5 ms a shader, which a new area can need dozens of in a frame).
What a new shader draws appears a frame or a few late the first time.
Instanced variants are always translated on the game's thread, and so is
every shader with `debug.gpu_dump_shaders`.

## Environment variables outside config.toml

These are read directly by the host (`port/knulli/host/`,
`port/android/host/`) or by the renderer, and have no `config.toml` key.

| Variable | Read by | Default | Effect |
| --- | --- | --- | --- |
| `HALO_FPS_LOG=<seconds>` | `host_sdl2.c` | off | Logs the frame rate, the longest frame, the frame-time histogram, resident memory, temperature and clocks at this interval. Also the interval of the `HALO_GL_TIMING` report. |
| `HALO_GL_TIMING=1` | `host_gl_timing.c`, `host_glthread.c` | off | Times every GL function and the GL thread's host operations, and the game's thread's waits. Reported with each `HALO_FPS_LOG` line, so it needs `HALO_FPS_LOG`. |
| `HALO_GPU_PASS_TIMING=1`, `2`, `3`, `4` | `host_glthread.c` | off | Finishes the GPU at each change of render target and times each pass; 2 and 3 trace one frame's passes and draws; 4 traces slow calls instead. Needs the GL thread. |
| `HALO_PROFILE_HZ=<rate>` | `host_profile.c` | off | Samples every thread at this rate; the samples are written when the game exits. |
| `HALO_PROFILE_DELAY=<seconds>` | `host_profile.c` | `0` | Starts the sampling this long after start-up. |
| `HALO_PROFILE_SAMPLES=<count>` | `host_profile.c` | `262144` | The samples kept (152 bytes each); the sampling stops when they are taken. |
| `HALO_PROFILE_THREADS=game` | `host_profile.c` | every thread | Samples only the game's thread (the one that marks its frames), so that a high rate costs the other threads nothing. |
| `HALO_PROFILE_FILE=<path>` | `host_profile.c` | `profile.txt` in the data folder | Where the profile goes. Each of the game thread's frames is marked among the samples (`profile.py --frames-over`). |
| `HALO_GL_THREAD=0` | `host_glthread.c` | on | Makes the GL calls on the game's thread, without the GL thread. |
| `HALO_GL_THREAD_FRAMES=<n>` | `host_glthread.c` | `1` | How many frames the game may be ahead of the GL thread. |
| `HALO_DIRECT_WRITES=0` | `host_glthread.c` | on | Queues the renderer's buffer writes for the GL thread to copy, instead of the game's thread copying them into the buffers itself ([Architecture](ARCHITECTURE.md#vertex-data-the-mirror-and-the-stream-ring)). |
| `HALO_ASYNC_PROGRAMS=0` | `host_glthread.c` | on | Builds shader programs on the GL thread instead of the program builders' threads: a new program stalls the frame (about 2 ms from the cache, 220 to 250 ms compiled) instead of appearing late. |
| `HALO_HITCH_LOG=<ms>` | `host_glthread.c`, `d3d8_gl.c` | off | The hitch log ([`debug.hitch_log`](#debughitch_log)). |
| `HALO_GL_FRAME_LOG=1` | `host_glthread.c` | off | Logs every 300 frames where the GL thread's frames went: waiting for the game's thread, running, waiting for a core, asleep in the driver, the frame pacing's hold and the swap ([Profiling](PROFILING.md#halo_gl_frame_log)). |
| `HALO_PACING_LOG=1` | `host_glthread.c` | off | Logs every 300 frames how evenly the frames reached the display, from the pans themselves; `2` also each late frame ([Profiling](PROFILING.md#halo_pacing_log)). |
| `HALO_DEBUG_SKIP_GL=glA,glB` | `host_glthread.c` | none | The GL thread does not make these calls. Needs the GL thread. |
| `HALO_SWAP_INTERVAL=<n>` | `host_sdl2.c` | the game's `display.vsync` | Overrides the swap interval; `0` turns vsync off. |
| `HALO_AUDIO_SAMPLES=<n>` | `host_sdl2.c` | `1024` | SDL2's audio buffer, in sample frames. |
| `HALO_DEBUG_COPY_BY_BLIT` | `d3d8_gl.c` | unset | Copies render targets by blits instead of `glCopyImageSubData`, to measure them. |
| `HALO_DATA_ROOT` | `host_main.c` | the executable's folder | The folder with `maps/` and `config.toml`. |
| `HALO_SAVE_ROOT` | `host_main.c` | `save/` in the data folder | The saved games and the shader cache. |
| `HALO_GUEST_IMAGE` | `host_main.c` | `halo_guest.elf` beside the executable | The guest image to load. |
| `HALO_DISPLAY_WIDTH` | `host_main.c` | from the framebuffer's mode | The width `display.screen_width = 0` uses. |
| `SDL_GAMECONTROLLERCONFIG` | SDL2 | set by `Halo.sh` | The controller mapping from `sdl_mapping.py`. |
| `HALO_FB_BUFFERS=<n>` | `tools/device/run.sh` | `2` | The number of framebuffers for a benchmark run (`fbset -vyres`). |

## Settings the handheld build ignores

The settings table also has desktop-only settings, which the handheld's
file does not contain: `display.fullscreen`, `display.window_scale`,
`input.mouse_sensitivity`, `input.invert_mouse`, `paths.data`,
`paths.saves`, `discord.application_id`, `debug.update_answer` and
`debug.hidden_window`. Their environment variables are still read. Two of
them matter: the host sets `HALO_DATA_ROOT` and `HALO_SAVE_ROOT` in the
game's environment, which is how the game learns its data and save folders.
